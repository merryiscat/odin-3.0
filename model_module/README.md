# model_module — 매매모델 모듈 (표준 플러그인)

> 데이터 흐름: **보다 → [판단(뒷부분)] → 실행 → 보여주다.** 마트(장터)의 단위.
> 2026-09-23 · 1호 모델 `rule-trade-v1` 구현(가상 계좌, 실제 주문 없음). 2026-09-28~10-02 일주일 가상 가동 뒤 검토 예정.

## 하는 일
매매 리스트(그날 볼 종목)와 시장 온도(상태값)를 받아서 → **"주문 의도"**(뭘·얼마·사라/팔라)를 낸다.
1호 모델은 실제 주문 대신 **가상 계좌**(현금·보유)를 스스로 관리하고, 모든 판단·근거·체결을 **모델 이름을 딴 SQLite 파일**에 남긴다.

- **읽기**(Supabase, 읽기 전용): `pick_list`(리스트 모델 `rule-pick-v1`) · `state_market_temp`(온도 `rule-temp-rt-v1`, 주간 `rule-temp-w-v0`) ·
  `raw_stock_ohlc`(종목 일봉 — 수량 산정·보유 평가·가상 체결가) · `dim_stock`(이름만).
- **쓰기**: `model_module/records/rule-trade-v1.sqlite` 만. Supabase에는 쓰지 않는다(`order_intent` 표는 아직 없음 — 실행 모듈이 생길 때 같이).

## 중요한 안전 규칙
- 모델은 **"임의 코드"가 아니라 "검증된 엔진 위의 설정/파라미터"** 로 만든다. 1호는 `trade_rules.py`의 숫자 상수가 그 파라미터다.
- 모델은 **제안만** 한다. 실제 주문·가드는 `execution_module`이 소유한다. 1호는 실행 모듈이 없으므로 **가상 체결만** 한다.
- 다른 모듈을 import 하지 않는다. DB 표로만 대화(`supa.py`는 그래서 복사본).

## 1호 모델 `rule-trade-v1` — 규칙 (사람이 읽는 원문, `trade_rules.py`와 1:1)

한 줄: **"리스트에서 돈이 들어오는 종목을 따라가되, 꼭지·얇은 종목·급락장은 피하고, 며칠 안에 나온다."** 규칙 버전 `trade-rules-v1`.

**언제**: 거래일 아침(장 전, 예약 08:30). 입력은 전부 "직전 거래일 종가까지"의 것. 오늘 낸 의도는 **오늘 시가에 체결된다고 가정**하고, 다음 실행에서 실제 시가(`raw_stock_ohlc.open`)로 가상 체결한다.

| 단계 | 규칙 번호 | 규칙 |
|---|---|---|
| 0 가상 체결 | `S_fill` | 지난 실행의 의도를 그날 시가로 채운다. 매도 먼저. 그날 일봉이 없으면 `unfilled_no_data`(무효), 시가가 없으면 `unfilled_no_trade`, 현금 부족이면 수량을 줄이거나 `unfilled_no_cash`, 보유 없는 매도는 `unfilled_not_held`. 수수료·세금 0 |
| 1 문(시장별) | `G1` | 직전 거래일 종가 판정(`rule-temp-rt-v1`, basis=eod)이 **급락(crash)** → 그 시장 **전량 매도** |
| | `G2` | 종가 판정이 **급락·투매(crash/selloff)** → 오늘 **매수 금지** |
| | `G3` | 주간 무드(`rule-temp-w-v0`)가 **긴급(emergency)** → 전량 매도 + 매수 금지 |
| | `G4` | 종가 판정 줄이 **없으면**(밤 배치 미실행 등) → 매수 금지(보수적). 매도·체결은 그대로 |
| | `A1` | 주간 무드가 **하락장·긴급**이면 매도 태도 `tight`, 아니면 `normal`. 주간 줄이 없거나 오래됐으면 normal + 표시 |
| 2 매도(보유 종목마다) | `X0` | 직전 거래일 일봉이 없으면 판단 보류(보유 유지) |
| | `X1` | 손절: 직전 종가가 평균 매입가 대비 **−5% 이하**(tight: −3%) |
| | `X2` | 익절: **+10% 이상** |
| | `X3` | 보유일 상한: 매입일 포함 **5거래일**(tight: 3거래일) 되면 매도 |
| 3 매수 후보(오늘 리스트 종목마다, 순서대로 걸고 첫 탈락 규칙 기록) | `B1` | 태그에 **돈 유입** 하나 이상: `new_high` / `money_surge` / `foreign_buy` / `inst_buy` / `both_buy` (`top_gainer`만으로는 안 산다) |
| | `B2` | `top_loser`(하락 상위)가 있으면 제외 |
| | `B3` | 경고 `blowoff`(꼭지) / `thin`(얇음) / `untradable` 있으면 제외 |
| | `B4` | 직전 거래일 등락률(`metrics.chg1_pct`) > 0 |
| | `B5` | 이미 보유 중이면 제외 |
| | `B6` | 직전 거래일 종가가 있어야 함(수량 산정) |
| 4 매수 결정 | `B7` | 통과 종목을 **점수 내림차순·순위 오름차순**으로, 시장별 **빈 자리**(최대 보유 3 − 현재 보유)와 **하루 신규 상한 2** 안에서 |
| | `B8` | 수량 = floor(min(1,666,666원, 남은 현금) ÷ 직전 종가). 1주도 못 사면 제외 |

숫자: 시작 현금 1,000만 원 · 시장별 최대 보유 3종목 · 하루 시장별 신규 2 · 종목 예산 = 1,000만 ÷ 6. 어떤 숫자든 바꾸면 `RULE_VER`를 올린다.
리스트는 **오늘 날짜(list_date)·구독 모델(rule-pick-v1)·아침 확정(phase=open)** 줄만 쓴다. 그 외 줄·다른 날짜 시세는 걸러지고 그 사실이 기록에 남는다.

### 왜 이렇게 (설계 메모)
- 리스트는 "살 종목"이 아니라 "볼 종목"(list_module 백테스트: 전날 급등주는 되돌림이 평균) → 꼭지(`blowoff`)·상승 상위만 있는 종목은 사지 않고, 돈 유입 태그를 요구.
- 시장 온도는 **오늘의 단면**이라 방향 예측이 아님(state_module 방향성 점검) → 문(gate)으로만 쓴다: 급락·투매 다음날 매수 금지, 급락이면 정리. 주간은 설계대로 **매도 태도**에만.
- 09-17 실데이터에서 두 시장 모두 매수 1건이 나오게 하되 규칙이 임의로 느슨하지 않게: 59종목 중 통과 2(코웨이·오이솔루션), 탈락 이유는 돈 유입 태그 없음 29 · 경고 27 · 하락 상위 1.

## 파일
| 파일 | 하는 일 |
|---|---|
| `trade_rules.py` | 규칙 원문의 코드판(순수 계산, DB·시계·무작위 없음 → 같은 입력 = 같은 출력). `run_day(inputs)` |
| `trade_data.py` | Supabase 읽기(리스트·온도·주간·종목 일봉·이름) |
| `trade_store.py` | SQLite 기록(run·run_input·rule_eval·intent·account·event) |
| `run_trade.py` | 하루 실행기(휴장·중복 확인 → 입력 스냅샷 → 규칙 → 기록). 오류도 기록하고 종료 코드 1 |
| `review_trade.py` | 주간 검토 — 기간을 주면 표로: 실행 회차 / 의도·체결 / **입력 스냅샷으로 독립 재계산해 적중·위반·놓침** / 탈락 이유 집계 / 결손 메모 / 오류 / (선택) 지금 DB와 비교 |
| `kr_calendar.py` | 휴장일 정적 표(2026). 해가 바뀌면 손으로 추가 |
| `tests/` | 규칙·기록·검토 테스트 10개(DB 없이) |
| `records/` | 기록 파일(`.sqlite`)·검토 결과. 깃 제외 |

## 실행 명령 (프로젝트 루트에서)
```
# 하루 실행(오늘) — 예약 실행이 부르는 것
uv run --project model_module python model_module/run_trade.py
# 특정 날짜를 시험 파일에 (실제 기록 파일과 분리)
uv run --project model_module python model_module/run_trade.py --date 2026-09-17 --db model_module/records/trial.sqlite
# 기록 없이 출력만
uv run --project model_module python model_module/run_trade.py --date 2026-09-17 --dry-run
# 테스트 한 줄
uv run --project model_module pytest model_module/tests
# 주간 검토 한 줄 (기간) — 표 출력 + 파일 저장. --refetch를 붙이면 그때 입력과 지금 DB를 비교(늦게 들어온 데이터)
uv run --project model_module python model_module/review_trade.py --from 2026-09-28 --to 2026-10-02 --refetch --out model_module/records/review_2026-09-28.md
```

## 잡 등록 (작업 스케줄러 — 기존 방식과 같음: `scripts/*.cmd` + schtasks)
`scripts/trade-day.cmd`가 하루 실행을 감싸고 `logs/trade-day.log`에 남긴다. 평일 **08:30**(리스트 밤 배치 뒤, 08:50 실시간 판별기 앞). 관리자 PowerShell에서 프로젝트 루트 경로로:
```
schtasks /Create /TN Odin3-trade /SC WEEKLY /D MON,TUE,WED,THU,FRI /ST 08:30 /TR "\"C:\Users\minhy\project\odin_3.0\scripts\trade-day.cmd\"" /F
schtasks /Run /TN Odin3-trade          # 즉시 시험 가동(오늘이 거래일이면 회차가 기록되고, 같은 날 두 번째는 skipped_duplicate)
schtasks /Query /TN Odin3-trade /V /FO LIST
```
휴장일·중복 실행은 스크립트가 스스로 기록(`status=holiday / skipped_duplicate`)하므로 스케줄은 평일 매일이면 된다.

**전제 — 입력이 매일 만들어져야 한다.** 이 모델은 `pick_list`(오늘 리스트)와 `raw_stock_ohlc`(직전 거래일 종목 일봉)를 읽는데,
2026-09-23 현재 리스트 쪽 잡은 **미등록**(보류 대장 14번: `refresh_dim_stock_master.py` 아침 / `collect_rank.py` 장중 /
`collect_stock_eod.py` 15:40 / `run_params.py` → `run_pick.py` 밤). 등록 전엔 매일 "리스트 없음 → 관망"만 기록되고, 매수 의도는 그날
일봉이 없어 `unfilled_no_data`가 된다(공공데이터 백필 `backfill_stock_ohlc_krx.py`로 뒤늦게 메워도 이미 무효 처리된 의도는 되살리지 않음 —
`--refetch`가 "그때 없었는데 지금 있음"으로 찍어 준다). 일주일 검증을 뜻 있게 하려면 **리스트 밤 배치(15:40 스냅샷 → 파라미터 → 리스트)를
먼저 등록**해야 한다.

## 기록 파일 (모델 이름을 딴 SQLite) — 무엇이 어디에
`model_module/records/rule-trade-v1.sqlite`
| 표 | 내용 |
|---|---|
| `run` | 회차: 거래일·시작/끝 시각·상태(ok / holiday / skipped_duplicate / error)·모드(live 예약 / manual 손 / dry)·직전 거래일·오류 문구·요약 |
| `run_input` | 그 회차가 본 입력 **원문 스냅샷**(list / state_rt / state_w / bars / calendar / account / pending_intents / names) |
| `rule_eval` | 규칙 하나·종목 하나마다 한 줄 — 걸렸나(fired)와 근거(detail). **안 걸린 이유도 여기** |
| `intent` | 주문 의도(거래일·시장·종목·방향·수량·기준가·규칙·근거) + 가상 체결(status·체결가·수량·메모) |
| `account` | 회차 끝 계좌(현금·보유). 다음 회차가 이어받는다 |
| `event` | 데이터 결손·지연 메모(리스트 없음, 종가 판정 없음, 주간 stale, 일봉 없음 …) |
안 돈 날은 `run`에 줄이 없다 → 주간 검토가 달력과 맞춰 **"실행 없음"** 으로 찍는다(휴장일은 "휴장(이유)").

## 가정 (사소해서 정하고 진행한 것 — 바꾸려면 여기와 `trade_rules.py`)
| # | 가정 | 왜 |
|---|---|---|
| 1 | 실행 시점 = 거래일 **아침**(08:30), 의도는 **그날 시가** 체결 가정 | 리스트가 "오늘 볼 종목"으로 아침에 확정되는 구조와 맞고, 미래 참조가 없다 |
| 2 | 가상 계좌 시작 현금 1,000만 원, 한 계좌로 두 시장 | 수량이 1주 이상 나오는 규모. 수익은 채점하지 않으므로 크기는 중요치 않음 |
| 3 | 수수료·세금 0, 체결은 시가 전량(현금 한도만 적용) | 가상·규칙 검증 목적 |
| 4 | 체결 확인은 **다음 실행 한 번만**. 그때 그날 일봉이 없으면 미체결 무효 | 뒤늦게 백필된 시세로 과거를 바꾸지 않기 위해(기록의 일관성) |
| 5 | 종가 판정이 없으면 매수 금지(보수적), 주간이 없으면 태도 normal | "모르면 사지 않는다" |
| 6 | 직전 거래일·거래일 여부는 **정적 휴장일 표**(`kr_calendar.py`)로 판단 | 데이터 결손과 휴장을 구분하려면 데이터 밖의 달력이 필요 |
| 7 | 경고(`thin`·`blowoff`)를 **배제**로 쓴다 | 리스트 규격은 "경고는 배제가 아니다"지만, 가상 계좌가 얇은 종목을 시가에 전량 산다는 가정이 비현실적이라 1호는 제외 |
| 8 | 보유일은 매입일 포함 거래일 수 | 단순·재현 가능 |
| 9 | 모델 등록: `dim_model`에 `rule-trade-v1`(kind=trade, dev) 한 줄 | 마트 명부 규약(model_id는 등록된 값만) |
| 10 | 2026-09-28(월)은 **거래일**(대체공휴일 아님 — 추석 09-24~26, 토요일 겹침은 대체 대상 아님) | 웹 확인 2026-09-23. 임시공휴일 지정 시 `kr_calendar.py`에 추가 |

## 아직 확인 못 한 것
- 예약 실행(스케줄러) 자체는 **등록하지 않았다**(등록 명령은 위). 등록 뒤 첫 실제 회차(mode=live)가 정상인지.
- 리스트 밤 배치 잡 미등록 상태에서 일주일을 돌리면 "리스트 없음" 회차만 쌓인다 — 등록 여부는 사용자 결정(보류 14번).
- `unfilled_no_cash`·`unfilled_not_held`·전량 정리(`G1`/`G3`)·익절(`X2`)은 테스트로만 확인, 실데이터에선 아직 안 나옴.
- Supabase `order_intent` 표에 의도를 같이 쓰는 것(실행 모듈 연결)은 미구현.

## 공개/비공개
- 플러그인 **틀·기본 모델**: 공개 가능. `records/`(가상 계좌 기록)는 깃 제외.
- **잘 되는(프리미엄) 모델**: 비공개.
