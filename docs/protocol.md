# 작업 프로토콜 — 단일 쓰기 스레드와 교차 검토 한 번

역할·모델·경로는 대상 프로젝트 `docs/roles.md`가 단일 출처. 이 문서는 절차와 종료 조건만 소유한다.
원본은 ohmypm 플러그인 `skills/kickoff-workspaces/PROTOCOL.md`, 프로젝트의 `docs/protocol.md`는 설치 시 복사본이다 — 절차를 고치면 원본을 고치고 다시 복사한다.

## 0. 이 구조가 남긴 것과 걷어낸 것 (2026-09-18 개정)

바깥 실측과 우리 네 바퀴를 대조해 **근거가 있는 부분만 남겼다**(`docs/research-multiagent.md`).

| 남긴 것 | 왜 |
|---|---|
| 스펙(관찰 가능한 완료 기준) | 요청을 글로 굳히는 값은 자리 수와 무관하다 |
| 교차 검토 **한 번** | 통제 실험에서 Codex 초안을 Claude가 검토하면 71.6→89.7%. **반대 방향은 91.4→82.8로 해롭다** |
| 검토자 재작성 금지 | 해로운 검토는 통째 재작성, 도움이 된 검토는 국소 지적 |
| 요청 원문 대조 | 실패 분류 1,642건에서 44.2%가 명세·설계, 32.3%가 전달 실패 |

| 걷어낸 것 | 왜 |
|---|---|
| 코디네이터 자리(pl3) | 어떤 근거도 지지하지 않았다. 배관이 최상위 모델 쿼터를 먹었다 |
| 오케스트레이션(run·task·gate·worker-start·check --wait) | 이벤트 소비자가 둘이 되며 병목을 만들었다(2026-09-18 실측) |
| 구현 워커 워크트리·병렬 | 감독자가 6/6 런에서 워커를 0명 골랐고, 강제 병렬은 토큰 5배·46~108% 더 느렸다 |

**구현은 main이 한다.** 바깥 합의가 "쓰기는 단일 스레드, 추가 에이전트는 action이 아니라 intelligence를 보탠다"이고,
핸드오프는 정보를 잃을 수만 있기 때문이다. 사용자가 진행을 화면으로 직접 보는 것도 덤이 아니라 핵심이다 —
"한세월 걸린다"의 절반은 다른 터미널에서 벌어지는 일을 폴링으로 지켜보던 시간이었다.

## 1. 차선 — 요청마다 같은 요금을 내지 않는다

**기본은 S다.** 되돌리기 어렵거나 운영에 닿을 때만 올린다. 사용자가 "가볍게"·"제대로"라고 하면 그게 이긴다.

| 차선 | 기준(하나라도 어긋나면 위 차선으로) | 절차 | 목표 |
|---|---|---|---|
| **S 즉시** | 되돌리기 쉽다(revert 한 번) · 운영 영향 없음 · 요청이 곧 완료 기준 | **main이 직접** 하고 커밋. 스펙·검토 없음 | 3~5분 |
| **M 표준** | 여러 파일 · 판단이 조금 필요 · 되돌릴 수 있음 | 스펙 한 장 → 검토 1회(차단만) → 10초 게이트 → main 구현 → 산출물 검토 1회 | 15분 |
| **L 중대** | 운영 환경 · 되돌리기 어려움(삭제·마이그레이션·외부 발신·구조 변경) · 미지 영역 | 아래 전부. 게이트는 스펙 전체 | 40분 |

반복 운영 업무는 첫 회 차선대로, 이후는 스펙 재사용(pl 턴 0).
S 판정이 틀려 커지면 그 자리에서 멈추고 M으로 올린다 — 되돌리기 쉬운 일만 S이므로 손해가 없다.

**착수할 때 차선과 예상 시간을 한 줄로 말한다.** 끝나면 실제 걸린 시간을 말하고 `docs/benchmark.md`에 한 줄 적는다.

## 2. 흐름

```
사용자 요청
  → main: 차선 판정 + 예상 시간 한 줄.  S면 여기서 직접 하고 끝
  → pl:   스펙 v1 (docs/tasks/T-NNN-<slug>.md)            ← Codex 켜는 순간 1
  → pl2:  검토 1회 — 요청 대조 + 차단 지적 (docs/reviews/T-NNN.review-v1.md)
  → pl:   지적마다 수용 / 근거 기각 → 스펙 v2             ← Codex 켜는 순간 2 (차단 있을 때만)
  → 사용자: 게이트 (M은 10초, L은 스펙 전체)
  → main: 구현. 진행이 화면에 보인다
  → pl2:  산출물 검토 1회 — 완료 기준마다 통과/실패, 고치지 않는다
  → main: 커밋·푸시 + 실제 시간 기록
```

## 3. 스펙 (pl)

`templates/task.md` 형식. **맨 위 `요청 원문`에 사용자가 한 말을 그대로 옮긴다** — 요약·해석·배경 추가 금지.
목표는 그 원문이 말하는 용도 한 문장이고 완료 기준은 거기서만 뽑는다.
이전 태스크를 예시로 걸 때는 **따를 것과 따르지 말 것을 같이** 적는다 — 양식을 가리키면 설계가 따라온다(2026-09-18 T-003).

크기는 **기준 개수가 아니라 줄 수로** 잰다. 기준 하나는 한 줄이다. 조항을 여럿 묶으면 개수 제한이 문단으로 우회된다.
완료 기준은 **관찰 가능한 문장**으로 쓴다 — "저장된다"가 아니라 "`GET /x`가 200과 `{"ok":true}`를 돌려준다".
기준 하나에 확인 방법 하나. 난이도 등급(S/M/L)과 근거를 적는다.

pl(Codex)은 종량 쿼터다. **스펙 v1과 v2를 쓸 때만 켠다.** pl이 하지 않는 것: 코드·`src/` 읽기,
코드 실행·테스트·설치·서버 기동(셸은 `docs/` 읽고 쓰는 용도로만 — Codex는 파일도 셸로 읽는다),
서브에이전트·ultra 모드, 스펙 한 장을 넘는 장문, 요청받지 않은 재작성.

## 4. 검토 (pl2) — 대상마다 한 번씩, 두 번

`templates/review.md` 형식. 검토는 **스펙에 한 번, 산출물에 한 번**이다. 같은 대상을 두 번 보지 않는다 —
재검토는 진짜 오류가 소진된 뒤 없는 문제를 만들고(정밀도 0.30→0.20) 산출물 대신 대화를 비평하는 쪽으로 표류한다.

규칙:
- **0번은 요청 대조다 — 건너뛰지 않는다.** 스펙의 `요청 원문`과 완료 기준이 같은 것을 말하는가.
  원문에 없는 산출물·열·행·판정이 기준에 있으면 **차단**. 원문 칸이 비어 있으면 그 자체가 차단.
  "지적 없음"으로 끝낼 때도 대조 한 줄은 적는다
- **재작성 금지.** 대안 문안을 통째로 쓰지 않는다. 지적은 "무엇이 / 왜 문제인가(근거) / 심각도 / 차단 여부"
- **지적마다 실패 시나리오를 붙인다.** 어떤 입력·상태에서 무엇이 틀어지는지 못 쓰면 그 지적은 버린다 —
  안 그러면 15건 중 12건이 노이즈가 된다(실무 보고)
- **산출물과 요청 원문을 본다.** 작성자의 사고 과정, 세션 로그, 이전 대화의 의도는 **주지도 보지도 않는다** —
  기획자의 추론을 읽으면 독립성이 깨지고 긴 맥락은 판단을 흐린다. 줄 것은 요청 원문·스펙·산출물뿐이다
- M 차선은 차단 항목만 10줄 이내, 차단이 없으면 "대조: 일치 / 지적 없음" 한 줄로 끝내고 v2를 부르지 않는다

**산출물 검토**(구현 후)는 스펙의 완료 기준마다 통과/실패를 판정해 스펙의 "검증" 절에 적는다.
**고치지 않는다** — 실패면 사유를 적어 main에 돌린다(2회까지). 스펙 자체를 고쳐야 하면 그때만 pl을 켠다.
M은 기준별 한 줄, 재조회·재실행은 차단 기준에만.

## 5. 반영 (pl)

지적마다 `수용`(무엇을 고쳤나) 또는 `기각`(근거)을 스펙의 "검토 반영" 절에 남긴다. 검토서는 고치지 않는다.
**차단 지적을 기각했다면 토론하지 않는다** — pl은 "차단 기각 있음"이라고 보고하고 멈추며, main이 사용자에게 올린다.

## 6. 게이트 (사용자)

- **M은 10초**: 용도 한 줄과 완료 기준 목록만 그대로 보이고 "이대로 갑니다" 한 줄. 생략하지 않는다 —
  사용자가 착수 전에 스펙을 보는 유일한 지점이고, 2026-09-18 T-003은 여기가 없어서 실패했다
- **L은 스펙 전체**: 목표·범위 밖·산출물을 두 문장으로 요약해 승인을 받는다

## 7. 구현 (main)

승인된 스펙의 완료 기준을 만족시킨다. **스펙 밖은 고치지 않는다** — 필요해지면 멈추고 사용자에게 묻는다.
오래 걸릴 명령은 백그라운드로 돌리고 진행 로그를 남긴다. 멈춤은 총 시간이 아니라 **진행 신호가 끊긴 채 오래**로 판정한다.
구현이 끝나면 완료 기준을 **항목별로** `통과/실패 + 확인한 방법`으로 적는다.
실행하지 않은 검증을 실행했다고 쓰지 않는다 — 안 됐으면 `실패`.

## 8. 세션 위생 — `/clear`와 `/compact`

세션은 쌓일수록 비싸고(종량 pl은 매 턴 전체 문맥을 다시 보낸다) 흐려진다. 기억은 세션이 아니라 **파일**에 있다.

| 자리 | `/clear` | `/compact` |
|---|---|---|
| pl (Codex) | **태스크마다** — v2 보고 뒤, 또는 "차단 기각 있음" 보고 뒤 | 안 한다(compact도 턴 비용) |
| pl2 (Claude 검토) | **검토서를 보고한 직후** — 들고 있을 상태가 없다 | 안 한다(검토는 한 턴) |
| main | 한 바퀴 끝난 뒤 | 세션이 길어졌는데 바퀴가 도는 중이면 |

공통: `AGENTS.md`·`CLAUDE.md`·`docs/protocol.md`·`docs/roles.md`가 바뀌면 **즉시** 비운다 — 시작할 때만 읽는다.
Orca를 재시작했으면 터미널 핸들이 바뀐다 — `orca terminal list --worktree name:pl`로 다시 잡는다.
**Git Bash에서 슬래시 명령을 보내지 않는다** — MSYS 경로 변환이 `/clear`를 `C:/Program Files/Git/clear`로 바꿔 텍스트로 꽂힌다(2026-09-18 두 번 실측). PowerShell에서 보내거나 `MSYS_NO_PATHCONV=1`을 앞에 붙인다.
**보내기 전 확인**: 화면에 "esc to interrupt / ctrl+b to run / Waiting for"가 있으면 일하는 중이다 — 그때는 아무것도 보내지 않는다.
**보낸 뒤 확인**: 화면을 읽어 새 대화 시작 화면인지 본다.

## 9. 벤치마크 — 구조를 감으로 판정하지 않는다

바퀴마다 `docs/benchmark.md`에 한 줄 적는다. **1회 런으로 결론 내지 않는다** — 같은 과제가 1회 성공 뒤
3회 연속 타임아웃한 사례가 있다. 판정은 **3바퀴 누적**으로 한다. 합격선과 철수선은 그 파일이 소유한다.

## 근거 (2026-09-17 조사, 2026-09-18 원문 재확인)

인용은 전부 실존을 확인했다. **둘은 우리가 잘못 읽었고, 아래에 기각으로 옮겼다.**

**쓰는 근거**
- **단일 패스가 다회차를 이긴다.** 검토를 반복하면 진짜 오류가 소진된 뒤 없는 문제를 만들고(거짓 양성 +62%, 정밀도 0.30→0.20) 산출물 대신 **대화 자체를 비평하는 쪽으로 표류**한다(Review Target Drift). 단일 패스 F1 0.376이 모든 다회차 변형을 이겼다 — [More Rounds, More Noise](https://arxiv.org/abs/2603.16244). → 검토 1회, 표류의 원인은 **이전 문답 맥락**이지 요청 원문이 아니다(2026-09-18 확인 — 그래서 요청 대조는 금지 대상이 아니다)
- **교차 벤더 검토는 방향이 있다.** Claude가 Codex 초안을 검토하면 71.6→89.7%, 반대 방향은 91.4→82.8%. 해로운 검토는 통째 재작성, 도움이 된 검토는 국소 수정 — [Cross-Model LLM Code Review](https://arxiv.org/abs/2607.21656). → 작성자 Codex·검토자 Claude, 검토자 재작성 금지
  - **적용 한계(중요)**: 대상은 **단일 파일 Python 경쟁 프로그래밍 116건**이고 스펙·설계 문서가 아니다. 오류 분류에 **요구사항 오해(requirement mismatch)가 없다** — 2026-09-18 T-003에서 우리가 실패한 종류를 이 논문은 다루지 않는다. 저자도 "exploratory"라고 적었다
  - 비용: 과제당 약 $0.25, **순 수정 1건당 약 $1.40**, 지연 38.5초→135.8초. 검토는 공짜가 아니다
- **아첨성 조기 합의는 단일 에이전트보다 못하다** — [Peacemaker or Troublemaker](https://arxiv.org/abs/2509.23055). → 토론하지 않는다, 차단 기각은 게이트로
- **동질 팀의 무구조 토론은 자기 수정보다 못하고 토큰을 2.1~3.4배 쓴다** — [The Cost of Consensus](https://arxiv.org/abs/2605.00914). → 역할을 나눌 거면 구조를 주고, 아니면 나누지 않는다
- 스펙 주도 개발: 기획·구현·검증 분리, 검증 가능한 완료 기준, 구현자가 아닌 별도 검증자 — [SDD in 2026](https://dev.to/krlz/spec-driven-development-in-2026-what-it-is-the-tooling-and-how-teams-actually-use-it-2fk2) (원문 미검증)

**기각한 인용 (2026-09-18)**
- [Revisiting MAD as Test-Time Scaling](https://arxiv.org/abs/2505.22960) — 우리 문서는 "이종 모델 조합만 일관되게 성능을 올렸다"의 근거로 걸었으나, **초록은 정반대에 가깝다**: 수학 추론에서 "agent diversity shows little benefit"이고, 다양성이 도움이 된 건 안전성 과제였다. 이종 구성의 근거는 위 Cross-Model 하나로 족하다
- [Agreement Drift](https://arxiv.org/abs/2604.11312) — 코드·과제 품질 논문이 아니라 **사회 시뮬레이션**(cs.SI) 논문이다. 동질성 네트워크에서 LLM 에이전트의 의견 이동을 본 것이고, 저자 결론은 "LLM 집단을 인간 집단의 대리로 보지 말라"이다. 검토 절차의 근거로 쓸 수 없다
