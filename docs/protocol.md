# ohmyPM 1.0 작업 프로토콜

derived_from: 사용자 합의 2026-09-21. 역할은 `roles.md`, 모델은 `workflow.json`, 명령은 `workflow-guide.md`.

## 요청과 합의
main에서 요청을 받는다. 작고 가역적이며 요청이 곧 완료 기준이면 main이 직접 처리한다.
설계가 필요하면 요청 원문·프로젝트 근거를 pl에 전달한다. pl은 사용자와 충분히 논의하며
완료 기준(최대 8개), 검증 방법, 작업 분해, 하네스, 병렬 독립성을 함께 정한다.
pl 질문은 main에 알리고 main은 사용자에게 pl 확인을 안내한다. 실제 논의는 사용자↔pl이다.
사용자가 특정 설계 버전의 구현을 요청해야 실행한다. 기준 변경은 재합의한다.

## 실행과 품질
main이 승인된 하네스를 작업 워크트리에 준비하고 준비 검사를 통과한 뒤 work를 시작한다.
컨테이너는 워크트리·독립 세션·특화 하네스·실행 설정의 묶음이며 OS 보안 경계가 아니다.
기존 도구를 우선 조합하고 새 도구는 설계 합의에 포함한다. 공용 설정을 임의 변경하지 않는다.
pl이 수정 영역·의존성·검증·자원의 독립성을 확인한 work만 최대 두 개 병렬로 진행한다.
work는 맡은 코드만 수정·커밋하고 실제 검증 근거를 제출한다. 기준을 바꿔 통과시키지 않는다.
pl이 코드를 읽고 work 환경에서 동작을 확인해 기준별 통과/실패를 판정한다. 미실행은 통과가 아니다.
실패는 work로 돌린다. pl이 코드를 대신 고치지 않는다. 상시 검토자 자리를 추가하지 않는다.

## 전달·중단·통합
원문·결정·버전별 스펙·manifest·결과는 파일, 알림은 `작업 ID / 버전 / 이벤트 / 자료 위치`다.
main이 실행 상태와 Orca inbox를 관리하고 pl이 설계·품질 판단을 소유한다. 상태는 Git 공통 디렉터리
`ohmypm-v1/`에 있다. 이벤트·실행 receipt가 불명확하면 재시작하지 말고 실제 자원을 대조한다.
설계를 바꾸기 전에 기존 work의 에이전트를 정산하고 변경을 보존한다. `retain` 후 `revise`할 수 있다.
품질 판정은 스펙 버전·내용 해시·결과 커밋·통합 기준 커밋에 연결된다. 어느 하나 바뀌면 재검증한다.
main은 깨끗한 등록 체크아웃에서 검증된 통합 커밋으로 fast-forward한다. 충돌은 work·pl로 돌린다.
원격 푸시·배포는 별도 요청이다. 머지와 증거 보존 및 터미널 정산을 확인해야 환경을 회수한다.
실패·미반영 코드·사용자의 새 변경은 유지한다. 작업 완료와 환경 회수 상태는 구분한다.

## 전환
0.x 작업은 소급 변환하지 않는다. 원본 플러그인과 설치된 복사본을 함께 갱신하고 새 작업부터 적용한다.
ohmypm에서 시범 운영 후 실제 작업의 누락·결함·수정 횟수·시간·비용을 단일 모델과 비교한다.
품질 향상은 측정할 가설이며 출시 버전만으로 입증되지 않는다. 점검·보고 기능 통합은 후속이다.
